## 0. Verdict (one paragraph)

The engineering is genuinely professional: modular, typed, locked, tested
(56 unit tests + full-engine smoke, all green), self-healing, and shipped in a
safe default (paper mode). The v19.3 → v20 rewrite fixed real, severe defects
(sizing/stop mismatch, phantom-PnL close loop, restart-lost daily state).
**However, this review found that the v20.6 headline numbers are not
reproducible from the repo as committed** — the pipeline that produced them is
missing, the numbers disagree with an honest re-run, and — most importantly for
operations — **the committed backtester's default signal cadence
(`SIGNAL_EVERY_N=3`) does not represent the live engine's cadence**, so the
backtest understates how often the live bot actually trades (54 trades vs 114
on the same data). The strategy itself (Donchian_Trend, 1h, symmetric)
**survives re-validation**: positive on train, positive on the unseen test
half, positive at both cadences, max drawdown ≈ 3–4%. The fix list below is
small and specific; none of it changes the "keep Donchian_Trend, trade rarely,
let winners run" thesis.

## 2. Findings

Severity: **P0** = money/correctness, **P1** = operational risk, **P2** = hygiene.

### P0

**F-01 · The v20.6 headline numbers cannot be reproduced from the repo.**
`analysis/data_1h/` (10,224 × 1h bars × 5 symbols) is committed, but **no
script in the repo runs the validation that produced the numbers in
`STRATEGY_v20.6.md`**. `validate_final.py` targets the gitignored 5m OKX
dataset (v20.1); `simulate.py --csv` defaults to `base_tf="5m"` (see F-04).
Re-running the documented claim with the shipped code (new script
`analysis/validate_donchian_1h.py`, same costs 0.05%/side + 2bps/side):

| Metric | Claimed (STRATEGY_v20.6.md) | Re-run, cadence 3h (committed default) | Re-run, cadence 1h (live-equivalent) |
|---|---|---|---|
| Full-sample return | +5.52% | **+4.69%** | **+7.10%** |
| Trades | 104 | 54 | **114** |
| Profit factor | 1.33 | 1.63 | 1.41 |
| Max DD | 4.04% | 3.09% | 3.89% |
| Win rate | 29.8% | 33.3% | 32.5% |
| By side | short +$61.6 / long −$6.4 | +$48.3 / −$1.4 | **+$4.3 / +$66.7** |
| Test-half (40%) return / PF | +3.52% / 1.53 | +3.00% / 1.75 | +3.94% / 1.59 |
| Walk-forward quarters | −0.72 / +0.21 / +0.50 / +5.27 | +0.91 / +0.24 / +5.27 / −1.36 | — |

Reading this carefully:

* The **strategy is real**: every honest variant is positive out-of-sample
  with a shallow drawdown (worst case PF 1.41, maxDD 3.89%). The "keep
  Donchian_Trend" decision of v20.6 stands.
* The claimed "entire edge is in shorts" is **true at live-equivalent cadence**
  (shorts +$66.7, longs +$4.3) and approximately matches the claimed trade
  count (114 vs 104) — the v20.6 run was evidently done with per-bar signal
  evaluation, which the committed harness does *not* do by default.
* The exact headline numbers (+5.52%, 104, 4.04%) match neither cadence, so
  whatever generated them (balance, fee buffer, code state) is not the shipped
  code. The document must be corrected to reproducible numbers; the new
  reproducible pipeline is committed with this review.
* **Parameter plateau re-verified**: 48/48 combinations of
  `entry_len ∈ {30,40,50,60} × sl_m ∈ {2.0,2.5,3.0} × break_atr ∈
  {1.4,1.5,1.6,2.0}` are **positive on the unseen test half**
  (+0.58% … +4.61%, PF 1.26 … 3.52). This is a broad plateau, not a lucky
  cell — the strongest robustness evidence in the repo, and it survives an
  independent re-run.

**F-02 · Backtest cadence ≠ live cadence (the strategy layer's biggest
fidelity gap).** Live: `scan_loop` runs every ~70s, so a breakout on any 1h
close is acted on within a minute. Backtest (base_tf=1h): signals are only
evaluated when `i % signal_every_n == 0` with the default 3 — i.e. only 00:00,
03:00, 06:00, … bars. Consequence measured on the same data: **54 trades vs
114**, and a *different* long/short PnL split (F-01 table). The `SIGNAL_EVERY_N`
constant was designed for the 5m base (3 × 5m = 15m cadence, which then was
live-like); for the 1h base it silently became 3h. The v20.6 headline
validation ran per-bar; the shipped harness default does not.
*Fix:* make cadence explicit per base TF — default `signal_every_n=1` for
`base_tf="1h"` (evaluate every closed bar), keep 3 for 5m; document it.

**F-03 · Stale signal anchor inflates realized risk at the fill.** The signal
builds `entry/sl/tp1/tp` from the **last closed bar's close**
(`signals.py::_build`), then:
* backtest fills at the **next bar's open** (`backtester.py::_execute_pending`),
* live fills at the **current market price** up to ~59 min later (scan loop
  keeps the signal alive until `ENTRY_COOLDOWN`/execution).

For a breakout, the fill price is typically already past the channel edge, so
the *realized* stop distance (fill → sl) is larger than the 2.5×ATR the sizer
budgeted (`position_sizer.py::compute` sizes off `|price−stop|` at signal
time). Actual risk per trade therefore exceeds `RISK_PCT` by an uncontrolled
margin (and the cost gate in `_build` is evaluated on the stale price too).
*Fix:* re-anchor `sl/tp1/tp` to the **actual fill price**, preserving the
intended distances, in both `_execute_pending` and `executor.try_open`, and
re-check the cost gate after re-anchoring.

### P1

**F-04 · `simulate.py --csv` mislabels the base timeframe.** With 1h CSVs it
constructs `Backtester(..., base_tf="5m")` by default: bar_seconds=300, the
"15m/1h" context slots become 3h/12h resamples, cooldowns (3600s) and daily
rolls (288 bars) are all 12× wrong. The README's own recommended validation
command (`python simulate.py --csv ./data`) is therefore misleading for the
currently shipped 1h strategy. *Fix:* `--tf {5m,1h}` flag, defaulting per the
bar spacing of the CSV.

**F-05 · Backtest HTF context ≠ live HTF context (latent).** For `base_tf=1h`,
the backtester resamples the "1h" slot over 24 bars → **daily** context, while
live feeds `htf_timeframe=4h`. Harmless *today* (Donchian_Trend reads only the
primary TF) but any future strategy that uses `ctx.tf1` would be validated on
a different context than it trades. *Fix:* expose the context TFs in
`TF_PRESETS` (mid=4h ⇒ 4 bars, htf=4h ⇒ 4 bars) instead of the 4/24 mapping.

**F-06 · API secret travels in plaintext on every request.** ✅ *Fixed in
v21.1 (2026-08-28, cycle 2).*
`signing.py::headers()` sent `X-API-Secret: <raw secret>` alongside the
HMAC-signed headers, while the module docstring claimed "the secret never
appears in the signature payload — only the derived HMAC". The published
OpenAPI spec of the exchange (`/openapi.json`) defines **no security
scheme**, so the header's necessity cannot be proven from the docs; the
working production contract (v19.3+) sends it, so it stays **on by default**
for compatibility. It is now a config flag — `ARIAX_SEND_SECRET_HEADER`
(`send_secret_header`, default `true`) — and the risk is documented in
`signing.py`, `.env.example` and `GO_LIVE_CHECKLIST.md` §2 (probe procedure:
verify one private call works without it, then set `false`). Unit-tested:
header present by default, absent when disabled, HMAC unchanged either way.
*Note:* the two tokens pasted into the project chat (GitHub PAT, `rnd_…` key)
are exposed and must be revoked regardless.

**F-07 · Dashboard has no authentication by default.** ✅ *Fixed in v21.1.*
`DASH_TOKEN` used to be optional; the service is deployed public (Render
free tier). `/api/status` exposes balance, positions, recent errors and the
paper/live flag to anyone who knows the URL. *Now:* auth is **on by
default** in `web.py::create_app` — with `DASH_TOKEN` unset a random token
is generated per process start and logged (dashed, so it survives the
log-redaction filter), and every route except `/health` requires
`?token=…` (or `X-Dash-Token`), constant-time compare. The dashboard page's
JS now carries the URL token on its XHRs so the UI keeps working.
`GO_LIVE_CHECKLIST.md` §2 tells the operator to set a stable `DASH_TOKEN` in
the deployment env. Unit-tested: 401 without token, 200 with query or
header token, 401 on wrong token, `/health` open, auto-generated token
actually works.

**F-08 · `real_test_trade` bypasses paper mode and every risk gate.** ✅
*Fixed in v21.1.*
The Telegram "⚡ REAL TEST" button placed a **real** market order even with
`PAPER_MODE=true` (verified: `ariax_client.place_order` always hits the live
`/api/order` endpoint), at a fixed `TEST_USD`, with hard-coded 3%/1.5%/3%
SL/TP, and closes it 12s later by force. That is an intentional manual
instrument — but it was the one path that could spend real money while the
dashboard says PAPER, on a **single tap**. *Now:* the button is labelled
"⚡ REAL TEST (real $)" and opens a confirmation prompt
(`_tg_realtest_prompt`) — the order is placed only by the explicit
`cmd_realtest_yes` arm; `cmd_realtest_no` cancels. The flow is
unit-tested end-to-end: tap 1 sends the prompt and places no order, tap 2
places exactly one order, and the menu label asserts the real-money warning.
